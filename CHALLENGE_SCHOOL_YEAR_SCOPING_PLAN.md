# Challenge School-Year Scoping Plan — Re-earnable Challenges + Perfect Seeder Data

> **Status:** Implemented on 2026-09-29. Migration `20260929150000_challenge_school_year_scoping`
> applied; catalog provisioning, SY-scoped scope resolution, admin year badge/filter, seeder
> upgrades and tests (S11, C1, C2) are in place. Seeding is done by the admin via the button.
> **Motivation:** The Data Seeder surfaced a cross-year defect: after a rollover, seeding the
> new school year fails with `Unique constraint failed (user_id, challenge_id)` — and even if
> it didn't, students could never earn the same challenge twice in their entire SORT lifetime.

---

## 1. Problem (verified)

| # | Finding | Evidence |
| --- | --- | --- |
| 1 | A DB unique index allows a challenge reward **once per user, ever** | migration `20260908_points_system_overhaul`: `point_histories_user_challenge_unique` on `(user_id, challenge_id)` |
| 2 | The live award path deliberately skips repeat rewards | `challenge-progress.service.ts:50` — `findFirst({ userId, challengeId })` |
| 3 | Challenge rows are keyed only by `(code, quarterCode)` and **survive rollover** | `schema.prisma:305` `@@unique([code, quarterCode])`; `rollover.service.ts:251-252` deletes only progress + contributions |
| 4 | `db:seed` never refreshes an existing challenge, so its window stays on the **old** school year | `server/prisma/seed.ts:117-150` — `upsert({ update: {} })`; dates only set on `create` |
| 5 | Consequence: after rollover the same challenge id is reused → new-year completions can neither insert a reward row (unique violation) nor be rewarded (findFirst skip) | reproduced by the Data Seeder (`pointHistory.createMany` FK/unique error) |
| 6 | Challenges are only provisioned for **one** quarter at seed time, and only while its window matches `now` | `seed.ts:112-133`; `challenge-term.service.ts:54-61` |

**Net effect today:** Year 1 challenge completion ⇒ Year 2+ completion never rewarded; new-year
challenge windows are stale/invisible; the Data Seeder cannot generate realistic per-year
challenge history.

## 2. Goal

Every school year (and every term inside it) gets its **own challenge instances**, so:

1. Challenges are re-earnable each school year (and reset each term as intended).
2. The Data Seeder produces realistic challenge progress/rewards for **every** year of a
   4× rollover test, with no unique-constraint failures.
3. All historical data (point histories, certificates, contributions) survives untouched.

Non-goals: changing the term state machine (`getTermStatus`), certificate issuance rules,
or the points rank system.

## 3. Locked design (recommended)

1. **Scope challenges by school year.**
   - `Challenge.schoolYearId String?` + FK to `school_years` (`ON DELETE SET NULL`).
   - Unique becomes `@@unique([code, quarterCode, schoolYearId])`.
   - `point_histories_user_challenge_unique` stays as-is — it is now safe because each year
     has distinct challenge ids.
2. **Auto-provision instances per school year.** A new idempotent service creates the
   default catalog (and copies forward custom challenges from the previous year) for each
   term (`T1`/`T2`/`T3`) of the target year, with windows from that year's
   `academic_quarters`.
3. **Legacy rows** (`schoolYearId = null`) are treated as `GLOBAL` and remain readable; the
   migration backfills existing rows to the currently active school year.
4. **Seeder upgrades:** seed challenge progress for **all challenge instances of the active
   year** (per-term windows), not just the currently visible term. The existing
   `rewardedChallengePairs` guard stays as a harmless safety net.

## 4. Phases

### Phase 0 — Schema migration `challenge_school_year_scoping`

`server/prisma/schema.prisma`:

```prisma
model Challenge {
  // ...
  schoolYearId String?     @map("school_year_id")
  schoolYear   SchoolYear? @relation(fields: [schoolYearId], references: [id], onDelete: SetNull)
  @@unique([code, quarterCode, schoolYearId])
  @@index([schoolYearId])
}
```

SQL (generated by `npx prisma migrate dev --name challenge_school_year_scoping`):

1. `ALTER TABLE challenges ADD COLUMN school_year_id TEXT;`
2. Backfill to the single active year when one exists:
   `UPDATE challenges SET school_year_id = (SELECT id FROM school_years WHERE is_active AND NOT is_archived ORDER BY start_date DESC LIMIT 1);`
3. Drop `challenges_code_quarter_code_key`, create
   `challenges_code_quarter_code_school_year_id_key`.
4. Add FK `ON DELETE SET NULL` + index.

SchoolYear gets the back-relation `challenges Challenge[]`.

### Phase 1 — Challenge catalog & provisioning service

New `server/src/services/challenge-catalog.service.ts`:

- `DEFAULT_CHALLENGE_CATALOG` — move the two current definitions out of `seed.ts`
  (`WEEKLY_RECYCLING_PIONEER`, `ZERO_SINGLE_USE_PLASTICS`).
- `ensureChallengesForSchoolYear(schoolYearId, { forceWindows? })`:
  1. Load that year's `academic_quarters` (T1/T2/T3).
  2. Determine definitions: if the year is new, copy every `Challenge` from the
     previous active/archived year (preserves admin-created challenges); if none exist,
     use `DEFAULT_CHALLENGE_CATALOG`.
  3. Upsert per `(code, quarterCode, schoolYearId)` — create missing; **refresh the window
     only when it is stale** (`endDate < term.startDate` or null) so intentional admin edits
     are not clobbered. `forceWindows` exists for an explicit admin refresh.
  4. Idempotent; returns `{ created, updated, skipped }`.
- Call sites:
  | Where | What |
  | --- | --- |
  | `rollover.service.ts` (after new SY activation, step 5/6) | copy previous year's definitions into the new year |
  | `ensureSchoolYear` first-time setup | provision from the default catalog |
  | `syncTermCalendar` (after quarter dates update) | refresh stale windows (handles the rollover/sync race in `/api/sync/all`) |
  | `server/prisma/seed.ts` | replace the two hardcoded upserts with `ensureChallengesForSchoolYear(activeSY)` |
  | `runDataSeed()` (defensive) | if the active year has zero challenges, provision before planning — lets the button self-heal years rolled over before this fix |

### Phase 2 — Scope resolution & award path

- `challenge-term.service.ts`:
  - `ChallengeScope` gains `schoolYearId: string | null`.
  - `resolveChallengeScope()` resolves the active school year (`getActiveSchoolYearId`) and
    includes `OR: [{ schoolYearId: activeSyId }, { schoolYearId: null }]` so legacy/global
    rows keep working during the transition.
- `challenge-progress.service.ts` `findActiveChallenges` filters by `schoolYearId` (union
  above) in addition to `quarterCode`.
- `report-points.service.ts` / `handleChallengeCompletion` unchanged — uniqueness is now per
  challenge instance, so year 2 rewards insert cleanly.
- Rollover keeps deleting `user_challenge_progress` + `challenge_contributions` (fresh term
  state); old challenge rows and point histories stay for history.

### Phase 3 — Admin API & UI

`server/src/routes/challenge.routes.ts`:

- `GET /` and `GET /admin`: default to the active `schoolYearId`, with an optional
  `?schoolYearId=` to inspect history; include `schoolYearId` + `schoolYearLabel` in the
  response.
- `POST /`: set `schoolYearId` (active SY by default), uniqueness check by
  `(code, quarterCode, schoolYearId)`.
- `PATCH /`: code-conflict check scoped to the same SY.
- No delete/immutability semantics change.

Frontend:

- `src/types/index.ts` — add `schoolYearId`/`schoolYearLabel` to `Challenge`/`AdminChallenge`.
- `AdminChallengesTab.tsx` — show the term + school-year badge; optional year filter
  (default: active year). No student-facing change (`GamificationTab` remains term-scoped).

### Phase 4 — Data Seeder upgrades

- `runDataSeed()` replaces the "visible term only" query with **all challenge instances for
  the active school year** (fallback to visible scope if none), passing each challenge's own
  window to the planner.
- Planner already applies `challenge.startDate/endDate` per report → challenge completions
  land in the correct term, for each instance; per-year instances make rewards re-earnable.
- Keep `rewardedChallengePairs`; add a note that it only triggers when an instance id is
  genuinely reused.
- Result stats unchanged (`challengeCompletions` now counts across the year's terms, which
  is the realistic number).

### Phase 5 — Tests

- Update/extend `data-seeder.test.ts`:
  - S6: completions fire per distinct challenge instance (T1 and T2 instances → both rewarded).
  - S10: pair-guard still blocks only the same instance id (cross-instance is allowed).
- New pure tests for catalog planning (definition × term expansion, stale-window rule,
  copy-forward) — keep the DB-touching part thin.
- Regression check: a simulated second-year instance with a new id produces a reward row even
  when the first-year id is already rewarded.
- Gates: `npm --prefix server run test:data-seed`, `npm --prefix server run build`,
  `npm run lint`, `npm run verify`.

### Phase 6 — Rollout

1. Backup DB → `npx prisma migrate dev` (or `migrate deploy` in prod) → verify backfill.
2. Run `ensureChallengesForSchoolYear(activeSy)` via `db:seed` or the seeder self-heal.
3. Re-run **Data Seeder → Replace this year's activity** on the current year.
4. Roll EnrollPro forward → sync → seed; confirm year 2 challenges get new ids and rewards
   are granted; repeat for the 4 rollovers.
5. Ledger/audit verification: each year shows its own challenge completions.

## 6. Risks & edge cases

- **Migration backfill** needs an active year; with none, rows stay `null` (legacy) and the
  first provision creates scoped rows.
- **Custom challenges**: copy-forward preserves them; stale-window-only refresh avoids
  overwriting admin edits.
- **Rollover/sync race**: `/api/sync/all` runs `runEnrollProSync` and `syncTermCalendar` in
  parallel; provisioning runs in both paths and is idempotent, and `syncTermCalendar`
  re-asserts correct windows afterwards.
- **Wipe/reset flows** already delete `challenges` (`wipe-tenant-data.ts:147`) — unaffected.
- **Certificates** read `AcademicQuarter` only; unaffected.
- **Legacy `null` rows** stay visible via the union scope — no "missing challenge" regression
  right after deploy.

## 7. Confirmed decisions (2026-09-29)

1. **Provision the default catalog for all terms (T1/T2/T3) of each school year** — every
   term gets its own challenge instances.
2. **Window refresh policy: stale-only** — update `startDate`/`endDate` only when they are
   null or point at a previous school year; never clobber intentional admin edits.
   (`forceWindows` remains available for an explicit admin refresh.)
3. **Admin Challenges tab: school-year badge + year filter** — default to the active year,
   allow inspecting previous years.
